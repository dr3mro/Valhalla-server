1/**
2 * @file gatekeeper.hpp
3 * @brief Facade over authentication, authorization and per-IP abuse detection.
4 * @details GateKeeper is the single "front desk" the rest of the server talks
5 * to for security. It exposes login/logout, session-or-JWT authentication
6 * checks, permission questions (create/read/update/delete and a few special
7 * cases, each in a normal and a coroutine version), and a request classifier
8 * used for abuse protection. It owns no algorithms of its own: every call is
9 * forwarded to a collaborator (SessionManager, TokenManager, DOSDetector,
10 * PermissionManager, PasswordWorker) fetched from the Store singleton. Because
11 * those collaborators are shared, separate GateKeeper objects all see the same
12 * sessions, tokens and counters.
13 *
14 * WHY THIS FILE MATTERS IN THE SERVER:
15 * This is the public face of the gatekeeper/security subsystem. Drogon
16 * controllers and filters create or receive a GateKeeper and call it to log a
17 * user in, decide whether a request is authenticated, check permissions before
18 * touching data, and ask whether an IP is abusing the service. GateKeeper
19 * itself calls down into the five manager classes listed above. Without this
20 * facade every controller would have to know all five managers and wire them
21 * together correctly; with it, security is reached through one simple, stable
22 * interface. The header declares the interface (what can be asked);
23 * gatekeeper.cpp holds the implementation.
24 *
25 * CONCEPTS TO LEARN (for beginners):
26 * - Facade pattern (one simple interface over several complex subsystems):
27 * https://en.wikipedia.org/wiki/Facade_pattern
28 * - JWT (a signed token carrying identity claims): https://jwt.io/introduction
29 * - Singleton / service locator (one shared instance looked up by type):
30 * https://en.wikipedia.org/wiki/Singleton_pattern
31 * - std::shared_ptr (shared ownership of an object):
32 * https://en.cppreference.com/w/cpp/memory/shared_ptr
33 * - std::optional ("a value that may be missing"):
34 * https://en.cppreference.com/w/cpp/utility/optional
35 * - Template function (one definition that works for many types):
36 * https://en.cppreference.com/w/cpp/language/function_template
37 * - Coroutine / co_await (pausing work without blocking a thread):
38 * https://en.cppreference.com/w/cpp/language/coroutines
39 * - Mutex/lock: https://en.cppreference.com/w/cpp/thread/mutex
40 * - HTTP status codes: https://developer.mozilla.org/en-US/docs/Web/HTTP/Status
41 *
42 * @author Amr Osman <dr3mro@gmail.com>
43 * @date 2026-11-16
44 */

86 /**
87 * @class GateKeeper
88 * @brief Facade over authentication, authorization and per-IP abuse
89 * detection.
90 * @details GateKeeper is the single entry point used by controllers and
91 * filters for: login/logout, validating a client's session or JWT,
92 * answering permission queries (synchronous and coroutine variants), and
93 * classifying requests for DoS/rate-limit purposes. It owns no algorithmic
94 * state of its own: every operation is delegated to a collaborator obtained
95 * from the Store singleton (SessionManager, TokenManager, DOSDetector,
96 * PermissionManager, PasswordWorker). Consequently, distinct GateKeeper
97 * instances share the same underlying managers, caches and state. Any
98 * thread-safety guarantees are those of the collaborators, not of
99 * GateKeeper itself.
100 * @note This class is polymorphic (the authentication validators are
101 * virtual) so it can be specialized in tests or alternative deployments.
102 * @see SessionManager, TokenManager, PermissionManager, DOSDetector,
103 * PasswordWorker
104 * @details For a beginner: a "facade" is like a receptionist. A controller
105 * does not need to know which manager to call or in what order; it just
106 * asks GateKeeper. Because the manager pointers are shared_ptrs obtained
107 * from a process-wide Store, building two GateKeepers does not create two
108 * sets of sessions - both talk to the same managers. The methods ending in
109 * "Async" are coroutine versions: they return a drogon::Task that the
110 * caller must drive, allowing slow database work to pause instead of
111 * blocking a server IO thread.
112 */

144 /**
145 * @brief Authenticates a client and issues a token, reporting the
146 * outcome through a callback.
147 * @details Parses the JSON credentials on the calling thread, reads the
148 * stored password hash with SessionManager, then dispatches the slow
149 * password verification and the state-changing work (session
150 * completion, token generation) to the password worker so no Drogon IO
151 * thread is blocked. Early failures (parse or hash lookup) are reported
152 * directly on the calling thread. Errors are caught and translated into
153 * an HTTP response via the CRITICALMESSAGERESPONSE macro.
154 * @param[in,out] callback Invoked exactly once with the HTTP status and
155 * either an error message or a JSON string containing
156 * token/username/client_id/group/ipAddress.
157 * @param[in] data JSON request body expected to contain "username" and
158 * "password".
159 * @param[in] ip_address Client IP, bound into the resulting token.
160 * @param[in] group Client group, used to select the session table.
161 * @details Step by step: validate the JSON, look up the hash, then hand
162 * the slow bcrypt check plus the database write and token creation to a
163 * worker thread. The callback is the "reply envelope" - it is called
164 * once with a status code and a body when the answer is ready, which
165 * may be later on another thread.

208 /**
209 * @brief Checks whether the supplied client is authenticated.
210 * @details Session cache first: if SessionManager reports a valid
211 * session, returns true immediately. Otherwise falls back to JWT
212 * validation via TokenManager; on a valid token, the session is
213 * (re)established with storeSession() and its result becomes the final
214 * answer. This cache-then-token ordering avoids a signature check on
215 * every request while still honouring token revocation data.
216 * @param[in,out] clientLoginData Identity/state accumulator; may be
217 * updated with session fields.
218 * @param[out] message Receives a human-readable reason on failure.
219 * @return True if an existing or freshly established session authorizes
220 * the client.
221 * @details "Cache first" is an optimization: checking a local session
222 * record is cheaper than verifying a signed token. Only when there is
223 * no live session does it pay for the token check, and a token that is
224 * about to expire is checked against the latest logout/active data from
225 * the database before being trusted.
226 */
227 virtual bool isAuthenticationValid(
228 std::optional<Types::ClientLoginData>& clientLoginData,
229 std::string& message);

231 * @brief Coroutine form of isAuthenticationValid().
