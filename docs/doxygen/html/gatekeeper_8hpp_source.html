1/**
2 * @file gatekeeper.hpp
3 * @brief Facade over authentication, authorization and per-IP abuse detection.
4 * @details GateKeeper is the single "front desk" the rest of the server talks to for security.
5 * It exposes login/logout, session-or-JWT authentication checks, permission questions
6 * (create/read/update/delete and a few special cases, each in a normal and a coroutine
7 * version), and a request classifier used for abuse protection. It owns no algorithms
8 * of its own: every call is forwarded to a collaborator (SessionManager, TokenManager,
9 * DOSDetector, PermissionManager, PasswordWorker) fetched from the Store singleton.
10 * Because those collaborators are shared, separate GateKeeper objects all see the same
11 * sessions, tokens and counters.
12 *
13 * WHY THIS FILE MATTERS IN THE SERVER:
14 * This is the public face of the gatekeeper/security subsystem. Drogon controllers and filters
15 * create or receive a GateKeeper and call it to log a user in, decide whether a request is
16 * authenticated, check permissions before touching data, and ask whether an IP is abusing the
17 * service. GateKeeper itself calls down into the five manager classes listed above. Without
18 * this facade every controller would have to know all five managers and wire them together
19 * correctly; with it, security is reached through one simple, stable interface. The header
20 * declares the interface (what can be asked); gatekeeper.cpp holds the implementation.
21 *
22 * CONCEPTS TO LEARN (for beginners):
23 * - Facade pattern (one simple interface over several complex subsystems): https://en.wikipedia.org/wiki/Facade_pattern
24 * - JWT (a signed token carrying identity claims): https://jwt.io/introduction
25 * - Singleton / service locator (one shared instance looked up by type): https://en.wikipedia.org/wiki/Singleton_pattern
26 * - std::shared_ptr (shared ownership of an object): https://en.cppreference.com/w/cpp/memory/shared_ptr
27 * - std::optional ("a value that may be missing"): https://en.cppreference.com/w/cpp/utility/optional
28 * - Template function (one definition that works for many types): https://en.cppreference.com/w/cpp/language/function_template
29 * - Coroutine / co_await (pausing work without blocking a thread): https://en.cppreference.com/w/cpp/language/coroutines
30 * - Mutex/lock: https://en.cppreference.com/w/cpp/thread/mutex
31 * - HTTP status codes: https://developer.mozilla.org/en-US/docs/Web/HTTP/Status
32 *
33 * @author Amr Osman <dr3mro@gmail.com>
34 * @date 2026-11-16
35 */

62 /**
63 * @class GateKeeper
64 * @brief Facade over authentication, authorization and per-IP abuse detection.
65 * @details GateKeeper is the single entry point used by controllers and filters for:
66 * login/logout, validating a client's session or JWT, answering permission
67 * queries (synchronous and coroutine variants), and classifying requests
68 * for DoS/rate-limit purposes. It owns no algorithmic state of its own: every
69 * operation is delegated to a collaborator obtained from the Store singleton
70 * (SessionManager, TokenManager, DOSDetector, PermissionManager, PasswordWorker).
71 * Consequently, distinct GateKeeper instances share the same underlying
72 * managers, caches and state. Any thread-safety guarantees are those of the
73 * collaborators, not of GateKeeper itself.
74 * @note This class is polymorphic (the authentication validators are virtual) so it can
75 * be specialized in tests or alternative deployments.
76 * @see SessionManager, TokenManager, PermissionManager, DOSDetector, PasswordWorker
77 * @details For a beginner: a "facade" is like a receptionist. A controller does not need to
78 * know which manager to call or in what order; it just asks GateKeeper. Because the
79 * manager pointers are shared_ptrs obtained from a process-wide Store, building two
80 * GateKeepers does not create two sets of sessions - both talk to the same managers.
81 * The methods ending in "Async" are coroutine versions: they return a drogon::Task
82 * that the caller must drive, allowing slow database work to pause instead of
83 * blocking a server IO thread.
84 */

105 /**
106 * @brief Authenticates a client and issues a token, reporting the outcome through a callback.
107 * @details Parses the JSON credentials on the calling thread, reads the stored password
108 * hash with SessionManager, then dispatches the slow password verification and
109 * the state-changing work (session completion, token generation) to the
110 * password worker so no Drogon IO thread is blocked. Early failures (parse or
111 * hash lookup) are reported directly on the calling thread. Errors are caught
112 * and translated into an HTTP response via the CRITICALMESSAGERESPONSE macro.
113 * @param[in,out] callback Invoked exactly once with the HTTP status and either an error
114 * message or a JSON string containing token/username/client_id/group/ipAddress.
115 * @param[in] data JSON request body expected to contain "username" and "password".
116 * @param[in] ip_address Client IP, bound into the resulting token.
117 * @param[in] group Client group, used to select the session table.
118 * @details Step by step: validate the JSON, look up the hash, then hand the slow bcrypt
119 * check plus the database write and token creation to a worker thread. The
120 * callback is the "reply envelope" - it is called once with a status code and a
121 * body when the answer is ready, which may be later on another thread.
122 */
123 void login(CALLBACK_&& callback, std::string_view data, const std::string& ip_address, std::string_view group);
124 /**
125 * @brief Coroutine form of login() for use on Drogon executor threads.
126 * @details Mirrors login() but awaits the stored-hash lookup cooperatively
127 * (SessionManager::fetchPasswordHashCoro) instead of blocking on it. The slow
128 * verification and all writes still run on the password worker. Early errors
129 * and the final worker result are delivered through @p callback.
130 * @param[in,out] callback Completion callback, invoked with status and body/message.
131 * @param[in] data JSON request body containing the credentials.
132 * @param[in] ip_address Client IP bound into the token.
133 * @param[in] group Client group selecting the session table.
134 * @note The coroutine frame must remain alive until the awaited database read completes;
135 * callers must co_await (or otherwise drive) the returned task.
136 */
137 drogon::Task<void> loginAsync(CALLBACK_&& callback, std::string_view data, const std::string& ip_address, std::string_view group);

149 /**
150 * @brief Checks whether the supplied client is authenticated.
151 * @details Session cache first: if SessionManager reports a valid session, returns true
152 * immediately. Otherwise falls back to JWT validation via TokenManager; on a
153 * valid token, the session is (re)established with storeSession() and its
154 * result becomes the final answer. This cache-then-token ordering avoids a
155 * signature check on every request while still honouring token revocation data.
156 * @param[in,out] clientLoginData Identity/state accumulator; may be updated with session fields.
157 * @param[out] message Receives a human-readable reason on failure.
158 * @return True if an existing or freshly established session authorizes the client.
159 * @details "Cache first" is an optimization: checking a local session record is cheaper
160 * than verifying a signed token. Only when there is no live session does it pay
161 * for the token check, and a token that is about to expire is checked against the
162 * latest logout/active data from the database before being trusted.
163 */
164 virtual bool isAuthenticationValid(std::optional<Types::ClientLoginData>& clientLoginData, std::string& message);
165 /**
166 * @brief Coroutine form of isAuthenticationValid().
167 * @details Same cache-then-token policy, but awaits TokenManager::isTokenValidCoro
168 * instead of blocking on the token check.

172 * @note Callers must drive the returned task; the frame must outlive the awaited read.
173 */
