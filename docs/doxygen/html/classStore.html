Detailed Description

Process-wide service locator that maps a type to one shared instance.

The class has no non-static state; the actual registry is a set of file-scope static members defined in store.cpp. Access is guarded by a single mutex, and a separate atomic generation counter lets per-thread caches notice replacements. Objects are owned through shared_ptr<void> and recovered by static_pointer_cast using typeid(T) as the key, so a lookup by type resolves to the concrete pointer stored for that type. 

     In plain words: a "singleton" is one single object shared by the

entire program. You never create a Store object; you just call its static functions. A shared_ptr is a smart pointer that keeps its object alive for as long as anyone still holds it, then destroys it automatically when the last holder lets go, so no manual delete is needed. typeid(T) is a small tag that identifies a C++ type while the program runs, which lets the map be keyed by type instead of by a name. A mutex is a lock that only one thread may hold at a time, which stops two threads from changing the map at once and corrupting it. static_pointer_cast simply relabels the generic stored pointer as a T pointer; it performs no runtime type check.

Note
registerObject refuses duplicates; getObject lazily constructs on first use; replaceObject overwrites without throwing and is intended for injecting test doubles. ("Lazily" means the object is not built until somebody actually asks for it; a "test double" is a fake object used in place of the real one during tests.)

◆ cachedObject()

template<typename T>
std::shared_ptr< T > Store::cachedObject ( )
inlinestaticnodiscard

Thread-local cached lookup of T, refreshed only when the Store generation changes.

Each thread keeps its own shared_ptr and the generation value it last saw. The generation is loaded with acquire semantics, pairing with the release fetch_add in replaceObject(), so a thread that observes a new generation also observes the replacement. A mismatch or an empty cache triggers a full getObject<T>() lookup; otherwise the cached pointer is returned without touching the mutex. 

     In plain words: looking in the registry needs a lock, which is

too slow to do for every web request. So each thread remembers the pointer it got last time. "Acquire" and "release" are a pair of promises: after replaceObject() publishes a new pointer with "release", any thread that reads the new number with "acquire" is also guaranteed to see that new pointer, not a stale one. This is cheap because a normal read of the counter is enough most of the time; the lock is only used when something actually changed.

TType to look up; on first use it must be constructible by getObject<T>() with no arguments.

◆ getObject()

template<typename T, typename... Args>
std::shared_ptr< T > Store::getObject ( Args &&... args)
inlinestaticnodiscard

Returns the singleton for T, constructing it on first use.

The fast path looks up the type under the mutex and returns the existing instance. On a miss the object is constructed outside the lock (see the inline comment below) and then re-checked under the lock before being published, so concurrent first calls cannot install two different instances. Constructor arguments are therefore only used on the first successful construction and ignored on later calls.

template<typename T, typename... Args>
std::shared_ptr< T > Store::registerObject ( Args &&... args)
inlinestatic

Explicitly creates and registers a singleton, rejecting a type that is already registered.

The duplicate check and the insertion use separate lock scopes so T's constructor runs without the mutex held. That keeps arbitrary constructor code, which may re-enter Store, from deadlocking on the inventory lock. ("Deadlock" means two operations waiting on each other forever.)

template<typename T>
void Store::replaceObject ( std::shared_ptr< T > obj)
inlinestatic

Overwrites the singleton registered for T and invalidates every thread-local cache.

Uses operator[] on the inventory, so it works whether or not T was registered before. The generation is incremented with release semantics so threads that acquire it in cachedObject() see the new pointer and re-fetch from the Store. ("Invalidates" means it makes every thread's saved pointer out of date.)
