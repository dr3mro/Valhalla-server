1/**
2 * @file staffcontroller.hpp
3 * @brief Implements staff management for one service entity type.
4 * @details In plain words, this file defines the class that actually carries out the three staff jobs
5 * declared in @ref StaffControllerBase - adding a member, removing a member, and inviting a
6 * member by email. Unlike the service controllers, this class is not an @ref EntityController,
7 * it inherits @ref Controller for the low-level "add/remove staff" database helpers and writes
8 * the job logic itself. For each job it reads the request, asks the authorisation service
9 * (GateKeeper) whether the caller is allowed, and only then does something — run SQL or send
10 * an HTTP request to the email daemon.
11 *
12 * WHY THIS FILE MATTERS IN THE SERVER:
13 * It is the concrete implementation behind the staff HTTP routes. The route layer calls these methods
14 * through @ref StaffControllerBase (with a `std::variant` choosing the entity type); each call lands here,
15 * where permission is checked before any change is made. It calls into @ref Controller for SQL,
16 * @ref GateKeeper for permission decisions and the email daemon for invitations. Without it, there would
17 * be no code to add, remove or invite staff, and the staff interface would have nothing behind it.
18 *
19 * CONCEPTS TO LEARN (for beginners):
20 * - std::shared_ptr (a smart pointer that shares ownership of an object): https://en.cppreference.com/w/cpp/memory/shared_ptr
21 * - Forward declarations (telling the compiler a type exists before defining it): https://en.cppreference.com/w/cpp/language/declarations
22 * - C++20 coroutines (functions that pause and resume with co_await/co_return): https://en.cppreference.com/w/cpp/language/coroutines
23 *
24 * @author Amr Osman <dr3mro@gmail.com>
25 * @date 2026-11-16
26 */

50/**
51 * @class StaffController
52 * @brief Implements staff management for one service entity type.
53 * @tparam T Service entity type (e.g. `Clinics`); no concept constraint is declared, but the
54 * implementation relies on `T` constructing from @ref api::v2::Types::StaffData and on
55 * `T::getSqlAddStaffStatement` / `T::getSqlRemoveStaffStatement` being available through
56 * @ref Controller.
57 * @details Unlike @ref ServiceController this is not an `EntityController`: it inherits @ref
58 * Controller for the low-level add/remove-staff SQL helpers and implements the domain
59 * operations of @ref StaffControllerBase directly. Each operation parses the request
60 * body, obtains a `GateKeeper` staff-management decision, and only then performs a side
61 * effect (an SQL statement, or an HTTP POST to the email-sender daemon for invites).
62 *
63 * Plain-language version: `T` is the concrete entity (say `Clinics`). The class relies on `T`
64 * being constructible from staff data and on `T` providing the add/remove staff SQL statements;
65 * those are compile-time expectations rather than an enforced concept. The three jobs here do
66 * real work (parse, check permission, act), unlike the pure forwarding service controllers.
67 *
68 * Explicit instantiations exist for `Clinics`, `Pharmacies`, `Laboratories` and
69 * `RadiologyCenters`; the staff route registry stores instances as shared pointers and
70 * selects one by service name.
71 * @note Instances are shared across Drogon workers; the cached dependencies below are populated
72 * in the constructor and are not mutated by the operations.
73 * @see StaffControllerBase, Controller, GateKeeper, Configurator
74 */
