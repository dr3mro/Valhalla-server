1/**
2 * @file staffcontroller.hpp
3 * @brief Implements staff management for one service entity type.
4 * @details In plain words, this file defines the class that actually carries
5 * out the three staff jobs declared in @ref StaffControllerBase - adding a
6 * member, removing a member, and inviting a member by email. Unlike the service
7 * controllers, this class is not an @ref EntityController, it inherits @ref
8 * Controller for the low-level "add/remove staff" database helpers and writes
9 * the job logic itself. For each job it reads the request, asks the
10 * authorisation service (GateKeeper) whether the caller is allowed, and only
11 * then does something — run SQL or send an HTTP request to the email daemon.
12 *
13 * WHY THIS FILE MATTERS IN THE SERVER:
14 * It is the concrete implementation behind the staff HTTP routes. The route
15 * layer calls these methods through @ref StaffControllerBase (with a
16 * `std::variant` choosing the entity type); each call lands here, where
17 * permission is checked before any change is made. It calls into @ref
18 * Controller for SQL,
19 * @ref GateKeeper for permission decisions and the email daemon for
20 * invitations. Without it, there would be no code to add, remove or invite
21 * staff, and the staff interface would have nothing behind it.
22 *
23 * CONCEPTS TO LEARN (for beginners):
24 * - std::shared_ptr (a smart pointer that shares ownership of an object):
25 * https://en.cppreference.com/w/cpp/memory/shared_ptr
26 * - Forward declarations (telling the compiler a type exists before defining
27 * it): https://en.cppreference.com/w/cpp/language/declarations
28 * - C++20 coroutines (functions that pause and resume with co_await/co_return):
29 * https://en.cppreference.com/w/cpp/language/coroutines
30 *
31 * @author Amr Osman <dr3mro@gmail.com>
32 * @date 2026-11-16
33 */

70/**
71 * @class StaffController
72 * @brief Implements staff management for one service entity type.
73 * @tparam T Service entity type (e.g. `Clinics`); no concept constraint is
74 * declared, but the implementation relies on `T` constructing from @ref
75 * api::v2::Types::StaffData and on `T::getSqlAddStaffStatement` /
76 * `T::getSqlRemoveStaffStatement` being available through
77 * @ref Controller.
78 * @details Unlike @ref ServiceController this is not an `EntityController`: it
79 * inherits @ref Controller for the low-level add/remove-staff SQL helpers and
80 * implements the domain operations of @ref StaffControllerBase directly. Each
81 * operation parses the request body, obtains a `GateKeeper` staff-management
82 * decision, and only then performs a side effect (an SQL statement, or an HTTP
83 * POST to the email-sender daemon for invites).
84 *
85 * Plain-language version: `T` is the concrete entity (say `Clinics`).
86 * The class relies on `T` being constructible from staff data and on `T`
87 * providing the add/remove staff SQL statements; those are compile-time
88 * expectations rather than an enforced concept. The three jobs here do real
89 * work (parse, check permission, act), unlike the pure forwarding service
90 * controllers.
91 *
92 * Explicit instantiations exist for `Clinics`, `Pharmacies`,
93 * `Laboratories` and `RadiologyCenters`; the staff route registry stores
94 * instances as shared pointers and selects one by service name.
95 * @note Instances are shared across Drogon workers; the cached dependencies
96 * below are populated in the constructor and are not mutated by the operations.
97 * @see StaffControllerBase, Controller, GateKeeper, Configurator
98 */
