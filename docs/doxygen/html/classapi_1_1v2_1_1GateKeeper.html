Detailed Description

Facade over authentication, authorization and per-IP abuse detection.

GateKeeper is the single entry point used by controllers and filters for: login/logout, validating a client's session or JWT, answering permission queries (synchronous and coroutine variants), and classifying requests for DoS/rate-limit purposes. It owns no algorithmic state of its own: every operation is delegated to a collaborator obtained from the Store singleton (SessionManager, TokenManager, DOSDetector, PermissionManager, PasswordWorker). Consequently, distinct GateKeeper instances share the same underlying managers, caches and state. Any thread-safety guarantees are those of the collaborators, not of GateKeeper itself.

Note
This class is polymorphic (the authentication validators are virtual) so it can be specialized in tests or alternative deployments.
See also
SessionManager, TokenManager, PermissionManager, DOSDetector, PasswordWorker

For a beginner: a "facade" is like a receptionist. A controller does not need to know which manager to call or in what order; it just asks GateKeeper. Because the manager pointers are shared_ptrs obtained from a process-wide Store, building two GateKeepers does not create two sets of sessions - both talk to the same managers. The methods ending in "Async" are coroutine versions: they return a drogon::Task that the caller must drive, allowing slow database work to pause instead of blocking a server IO thread.

Constructs the facade, resolving collaborators from the Store singleton.

Each collaborator is held via shared_ptr, so this object shares ownership of the process-wide instances rather than creating private ones.

In other words, construction just grabs five already-existing shared objects from Store; it does not open a database or start any threads itself.

◆ isAuthenticationValid()

bool GateKeeper::isAuthenticationValid ( std::optional< Types::ClientLoginData > & clientLoginData,
std::string & message )
virtual

Checks whether the supplied client is authenticated.

Session cache first: if SessionManager reports a valid session, returns true immediately. Otherwise falls back to JWT validation via TokenManager; on a valid token, the session is (re)established with storeSession() and its result becomes the final answer. This cache-then-token ordering avoids a signature check on every request while still honouring token revocation data.

Parameters
[in,out]clientLoginDataIdentity/state accumulator; may be updated with session fields.
[out]messageReceives a human-readable reason on failure.
Returns
True if an existing or freshly established session authorizes the client.

"Cache first" is an optimization: checking a local session record is cheaper than verifying a signed token. Only when there is no live session does it pay for the token check, and a token that is about to expire is checked against the latest logout/active data from the database before being trusted.

◆ login()

void GateKeeper::login ( CALLBACK_ && callback,
std::string_view data,
const std::string & ip_address,
std::string_view group )

Authenticates a client and issues a token, reporting the outcome through a callback.

Parses the JSON credentials on the calling thread, reads the stored password hash with SessionManager, then dispatches the slow password verification and the state-changing work (session completion, token generation) to the password worker so no Drogon IO thread is blocked. Early failures (parse or hash lookup) are reported directly on the calling thread. Errors are caught and translated into an HTTP response via the CRITICALMESSAGERESPONSE macro.

Parameters
[in,out]callbackInvoked exactly once with the HTTP status and either an error message or a JSON string containing token/username/client_id/group/ipAddress.
[in]dataJSON request body expected to contain "username" and "password".
[in]ip_addressClient IP, bound into the resulting token.
[in]groupClient group, used to select the session table.

Step by step: validate the JSON, look up the hash, then hand the slow bcrypt check plus the database write and token creation to a worker thread. The callback is the "reply envelope" - it is called once with a status code and a body when the answer is ready, which may be later on another thread.

Coroutine form of login() for use on Drogon executor threads.

Mirrors login() but awaits the stored-hash lookup cooperatively (SessionManager::fetchPasswordHashCoro) instead of blocking on it. The slow verification and all writes still run on the password worker. Early errors and the final worker result are delivered through callback.

Note
