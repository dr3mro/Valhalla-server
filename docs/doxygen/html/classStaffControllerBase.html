Detailed Description

Type-erased interface for service-staff management operations.

Exposes three domain operations — add, remove and invite — each in a synchronous callback form and a coroutine (drogon::Task<void>) form. The staff route registry holds concrete controllers behind this base and dispatches to them via a std::variant over the service entity type.

In plain words: "synchronous" means the caller gets the answer through a callback function, while the coroutine (drogon::Task<void>) versions can be paused with co_await so the server can do other work meanwhile. "Virtual dispatch" means a call made through this base automatically runs the real object's version. A std::variant is like a box that can hold one of several different controller types at a time.

Invocation contract shared by every method:

  • callback is std::function<void(int, const std::string&)>, it is moved through the call chain and, by contract, invoked once on each completion path, including failures. Its first argument is an api::v2::Http::Status code, the second a response body.
  • requester is the authenticated caller; implementations require permission to manage staff of the target service before performing any side effect.
  • data is a non-owning view of the raw JSON request body, valid only for the call; it must carry the target service id (id or nominee_id) used for authorisation.

The *Async methods must be co_awaited; the HTTP layer wraps them in drogon::async_run and builds the reply from the callback result.

Note
The interface itself is stateless; behaviour lives in StaffController.

Adds a staff member to a service entity.

Implementations parse a payload holding api::v2::Types::StaffData plus an id identifying the service, check staff-management permission, then execute the entity's add-staff statement. A malformed body is an exceptional (500) path here, not a 400 validation response.

Invites a staff member to a service entity by delegating delivery to the email daemon.

Implementations parse a nominee_id and the invite fields, check permission, build an invite message and POST it to the configured email-sender daemon. A 200 response echoes the daemon's body; malformed invite data or a failed send yields 400.
