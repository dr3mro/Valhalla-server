1/**
2 * @file staffcontrollerBase.hpp
3 * @brief Type-erased interface for service-staff management operations.
4 * @details In plain words, this file lists the three jobs that deal with the people who work for a
5 * service entity (a clinic, pharmacy, etc.): Add a staff member, Remove a staff member, and
6 * Invite a staff member by email. "Type-erased" means the rest of the server can call these jobs
7 * without knowing which exact kind of service is behind them. Each job appears twice: an ordinary
8 * version that reports its result through a callback (a "call me when you are done" function), and
9 * an "async" version that uses a coroutine (a function that can pause and resume later). This file
10 * only declares the jobs; the real work lives in the class that inherits from it.
11 *
12 * WHY THIS FILE MATTERS IN THE SERVER:
13 * This is the doorway the staff HTTP routes use to reach the concrete staff controller for any service
14 * type. Because the functions here are "virtual", one route handler can serve clinics, pharmacies,
15 * laboratories and radiology centers alike — the call is automatically forwarded to the right object
16 * (selected with a `std::variant`, a variable that can hold one of several types). This file calls into
17 * nothing itself, but it is the contract that @ref StaffController implements and that the route
18 * registry depends on. Without it, managing staff would need separate route code for each entity type.
19 *
20 * CONCEPTS TO LEARN (for beginners):
21 * - Virtual functions (calling the right version through a base pointer): https://en.cppreference.com/w/cpp/language/virtual
22 * - C++20 coroutines (functions that pause and resume with co_await/co_return): https://en.cppreference.com/w/cpp/language/coroutines
23 * - std::variant (a type-safe union holding one of several alternatives): https://en.cppreference.com/w/cpp/utility/variant
24 *
25 * @author Amr Osman <dr3mro@gmail.com>
26 * @date 2026-11-16
27 */

39/**
40 * @class StaffControllerBase
41 * @brief Type-erased interface for service-staff management operations.
42 * @details Exposes three domain operations — add, remove and invite — each in a synchronous
43 * callback form and a coroutine (`drogon::Task<void>`) form. The staff route registry
44 * holds concrete controllers behind this base and dispatches to them via a
45 * `std::variant` over the service entity type.
46 *
47 * In plain words: "synchronous" means the caller gets the answer through a callback
48 * function, while the coroutine (`drogon::Task<void>`) versions can be paused with co_await
49 * so the server can do other work meanwhile. "Virtual dispatch" means a call made through
50 * this base automatically runs the real object's version. A `std::variant` is like a box that
51 * can hold one of several different controller types at a time.
52 *
53 * Invocation contract shared by every method:
54 * - `callback` is `std::function<void(int, const std::string&)>`, it is moved through
55 * the call chain and, by contract, invoked once on each completion path, including
56 * failures. Its first argument is an @ref api::v2::Http::Status code, the second a
57 * response body.
58 * - `requester` is the authenticated caller; implementations require permission to
59 * manage staff of the target service before performing any side effect.
60 * - `data` is a non-owning view of the raw JSON request body, valid only for the call;
61 * it must carry the target service id (`id` or `nominee_id`) used for authorisation.
62 *
63 * The `*Async` methods must be co_awaited; the HTTP layer wraps them in
64 * `drogon::async_run` and builds the reply from the callback result.
65 * @note The interface itself is stateless; behaviour lives in @ref StaffController.
66 * @see StaffController, Controller, GateKeeper
67 */
