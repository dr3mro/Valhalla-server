Detailed Description

A fixed-size worker pool with a bounded queue, plus the callback-adapting helper built on it.

This file declares BoundedExecutor: a group of worker threads that run slow, blocking jobs such as database calls and password hashing away from Drogon's IO threads. Each worker has a short queue. If every queue is full, a new job is refused instead of being allowed to wait forever, so the server can quickly answer 503. The helper runOnExecutor() makes sure the HTTP reply is sent whether the job was accepted or refused.

WHY THIS FILE MATTERS IN THE SERVER: Drogon's IO threads must stay free to accept new requests. Database and password work would block them, so callers use runOnExecutor() to hand that work to this pool. The pool reports false when full, which lets the caller answer HTTP 503 ("server busy") rather than piling up unlimited work. With zero workers, jobs run inline on the caller, which is how unit tests stay synchronous. Without this file, every slow call would stall the whole web server.

CONCEPTS TO LEARN (for beginners):

  • Condition variables: a way for a thread to sleep until another thread wakes it with new work. https://en.cppreference.com/w/cpp/thread/condition_variable
  • Atomic memory order: rules for when one thread's writes become visible to another. https://en.cppreference.com/w/cpp/atomic/memory_order
  • Work stealing: an idle worker takes jobs from a busier worker's queue. https://en.wikipedia.org/wiki/Work_stealing
  • RAII: a local lock object that unlocks a mutex automatically when the scope ends. https://en.cppreference.com/w/cpp/language/raii

template<typename Body>
void runOnExecutor ( BoundedExecutor & executor,
CALLBACK_ && callback,
const char * busy_message,
Body && body )

Runs body(callback) on an executor, answering 503 immediately when the queue is full.

Runs body(callback) on the executor. When the queue is full the callback is answered right away with 503 and body never runs. The callback is shared with the task so that it is still available for that reply. 

     The callback is moved into a shared_ptr that both the queued task

and this function hold. On acceptance the task runs on a worker thread (or inline when the executor has no workers) and body receives the callback as an rvalue. On rejection the callback is invoked here, on the submitting thread, with SERVICE_UNAVAILABLE and busy_message; body is destroyed without being called. 

     In plain words: hand the slow job (body) and the HTTP reply function

(callback) to the pool. If the pool takes the job, a worker runs body later and body sends the reply. If the pool is full, we send a 503 right now using the same callback. Either way the client always gets an answer, and the callback is never lost.

Template Parameters
BodyCallable invocable with a CALLBACK_ (std::function<void(int, const std::string&)>); it is captured by the task, so it must be move-constructible.
