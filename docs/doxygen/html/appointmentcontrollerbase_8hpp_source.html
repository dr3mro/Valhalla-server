1/**
2 * @file appointmentcontrollerbase.hpp
3 * @brief Type-erased interface for appointment-entity CRUD+S operations.
4 * @details In plain words, this file lists the jobs every "appointment entity"
5 * must support. Those jobs are: Create a new appointment, Read one, Update one,
6 * Delete one, and Search through many — together called "CRUD+S". "Type-erased"
7 * is a fancy word for hiding the exact type: the rest of the server can call
8 * these jobs without knowing which kind of appointment is actually behind them.
9 * Each job appears twice: an ordinary version that reports its result through a
10 * callback (a "call me when you are done" function), and an "async" version
11 * that uses a coroutine (a function that can pause and resume later). This file
12 * only declares the jobs; the real work lives in the class that inherits from
13 * it.
14 *
15 * WHY THIS FILE MATTERS IN THE SERVER:
16 * This is the doorway the appointments HTTP routes use to reach every
17 * appointment controller. Because the functions here are "virtual", one route
18 * handler can serve clinics, pharmacies, laboratories and radiology-center
19 * appointments alike — the call is forwarded to the right concrete object
20 * (chosen with a `std::variant`, a box that can hold one of several types).
21 * This file calls into nothing itself, but it is called by the appointments
22 * route registry and it is the contract @ref AppointmentController fulfils.
23 * Without it, each appointment route would need separate code for every entity
24 * type.
25 *
26 * CONCEPTS TO LEARN (for beginners):
27 * - Virtual functions (calling the right version through a base pointer):
28 * https://en.cppreference.com/w/cpp/language/virtual
29 * - C++20 coroutines (functions that pause and resume with co_await/co_return):
30 * https://en.cppreference.com/w/cpp/language/coroutines
31 * - std::optional (a value that may be absent):
32 * https://en.cppreference.com/w/cpp/utility/optional
33 *
34 * @author Amr Osman <dr3mro@gmail.com>
35 * @date 2026-11-16
36 */

60/**
61 * @class AppointmentControllerBase
62 * @brief Type-erased interface for appointment-entity CRUD+S operations.
63 * @details Declares a synchronous callback form and a coroutine
64 * (`drogon::Task<void>`) form of every operation. The appointments route
65 * registry reaches concrete controllers through this base via a `std::variant`,
66 * so its virtual functions are the dispatch point used by a single route
67 * handler for all appointment entity types.
68 *
69 * In plain words: "synchronous" means the answer arrives through a
70 * callback function, while the coroutine (`drogon::Task<void>`) versions can be
71 * paused with co_await so the server can do other work meanwhile. "Virtual
72 * functions" mean a call made through this base runs the real object's version.
73 * A `std::variant` is a box that can hold one of several controller types.
74 *
75 * Invocation contract shared by every method:
76 * - `callback` is `std::function<void(int, const std::string&)>`, it
77 * is moved through the call chain and, by contract, invoked once on each
78 * completion path, including failures. Its first argument is an @ref
79 * api::v2::Http::Status code, its second a response body.
80 * - `requester` is the authenticated caller identity consulted for
81 * authorisation.
82 * - `data` is a non-owning view of the raw JSON request body, valid
83 * only for the call.
84 * - `_id` is the optional target id; absence is handled by the
85 * concrete implementation.
86 *
87 * The `*Async` methods must be co_awaited; the HTTP layer wraps them
88 * in `drogon::async_run` and turns the callback result into a reply.
89 * @note The interface itself is stateless; behaviour lives in @ref
90 * AppointmentController.
91 * @see AppointmentController, EntityControllerBase, Controller
92 */
