1/**
2 * @file appointmentcontrollerbase.hpp
3 * @brief Type-erased interface for appointment-entity CRUD+S operations.
4 * @details In plain words, this file lists the jobs every "appointment entity" must support. Those
5 * jobs are: Create a new appointment, Read one, Update one, Delete one, and Search through
6 * many — together called "CRUD+S". "Type-erased" is a fancy word for hiding the exact type:
7 * the rest of the server can call these jobs without knowing which kind of appointment is
8 * actually behind them. Each job appears twice: an ordinary version that reports its result
9 * through a callback (a "call me when you are done" function), and an "async" version that
10 * uses a coroutine (a function that can pause and resume later). This file only declares the
11 * jobs; the real work lives in the class that inherits from it.
12 *
13 * WHY THIS FILE MATTERS IN THE SERVER:
14 * This is the doorway the appointments HTTP routes use to reach every appointment controller. Because
15 * the functions here are "virtual", one route handler can serve clinics, pharmacies, laboratories and
16 * radiology-center appointments alike — the call is forwarded to the right concrete object (chosen
17 * with a `std::variant`, a box that can hold one of several types). This file calls into nothing itself,
18 * but it is called by the appointments route registry and it is the contract @ref AppointmentController
19 * fulfils. Without it, each appointment route would need separate code for every entity type.
20 *
21 * CONCEPTS TO LEARN (for beginners):
22 * - Virtual functions (calling the right version through a base pointer): https://en.cppreference.com/w/cpp/language/virtual
23 * - C++20 coroutines (functions that pause and resume with co_await/co_return): https://en.cppreference.com/w/cpp/language/coroutines
24 * - std::optional (a value that may be absent): https://en.cppreference.com/w/cpp/utility/optional
25 *
26 * @author Amr Osman <dr3mro@gmail.com>
27 * @date 2026-11-16
28 */

41/**
42 * @class AppointmentControllerBase
43 * @brief Type-erased interface for appointment-entity CRUD+S operations.
44 * @details Declares a synchronous callback form and a coroutine (`drogon::Task<void>`) form of
45 * every operation. The appointments route registry reaches concrete controllers through
46 * this base via a `std::variant`, so its virtual functions are the dispatch point used by
47 * a single route handler for all appointment entity types.
48 *
49 * In plain words: "synchronous" means the answer arrives through a callback function, while
50 * the coroutine (`drogon::Task<void>`) versions can be paused with co_await so the server can
51 * do other work meanwhile. "Virtual functions" mean a call made through this base runs the real
52 * object's version. A `std::variant` is a box that can hold one of several controller types.
53 *
54 * Invocation contract shared by every method:
55 * - `callback` is `std::function<void(int, const std::string&)>`, it is moved through the
56 * call chain and, by contract, invoked once on each completion path, including
57 * failures. Its first argument is an @ref api::v2::Http::Status code, its second a
58 * response body.
59 * - `requester` is the authenticated caller identity consulted for authorisation.
60 * - `data` is a non-owning view of the raw JSON request body, valid only for the call.
61 * - `_id` is the optional target id; absence is handled by the concrete implementation.
62 *
63 * The `*Async` methods must be co_awaited; the HTTP layer wraps them in
64 * `drogon::async_run` and turns the callback result into a reply.
65 * @note The interface itself is stateless; behaviour lives in @ref AppointmentController.
66 * @see AppointmentController, EntityControllerBase, Controller
67 */
