1/**
2 * @file servicecontroller.hpp
3 * @brief Service-entity controller that adapts @ref EntityController to @ref
4 * ServiceControllerBase.
5 * @details In plain words, this file defines a small "adapter" class for each
6 * kind of service entity (clinic, pharmacy, laboratory, radiology center). An
7 * adapter is a thin wrapper that passes a request straight through to another
8 * class that does the real work — here that class is
9 * @ref EntityController. Every job listed below (create, read, update,
10 * delete, search and their coroutine versions) simply forwards to the matching
11 * method of `EntityController<T>`. This class adds no behaviour of its own:
12 * validation, permission checks, building the database query, turning results
13 * into JSON and mapping errors to HTTP status codes all happen in that base.
14 *
15 * WHY THIS FILE MATTERS IN THE SERVER:
16 * It gives service entities their own interface, separate from appointment
17 * entities, so the route registry can pick the right controller family by name.
18 * The HTTP layer calls these methods through
19 * @ref ServiceControllerBase (using a `std::variant`), and each call lands here
20 * and is handed to
21 * @ref EntityController. If this file were missing, there would be no concrete
22 * class satisfying the service interface and no way to route a
23 * clinic/pharmacy/laboratory/radiology request to the real CRUD+S code.
24 *
25 * CONCEPTS TO LEARN (for beginners):
26 * - C++20 concepts / requires (compile-time checks on template arguments):
27 * https://en.cppreference.com/w/cpp/language/constraints
28 * - Templates (writing one class that works for many types):
29 * https://en.cppreference.com/w/cpp/language/templates
30 * - C++20 coroutines (functions that pause and resume with co_await/co_return):
31 * https://en.cppreference.com/w/cpp/language/coroutines
32 *
33 * @author Amr Osman <dr3mro@gmail.com>
34 * @date 2026-11-16
35 */

61/**
62 * @class ServiceController
63 * @brief Service-entity controller that adapts @ref EntityController to @ref
64 * ServiceControllerBase.
65 * @tparam T Service entity type; must satisfy @ref Service_t (derived from
66 * `Service`).
67 * @details A thin, stateless adapter: every CRUD+S entry point simply forwards
68 * to the same-named method of `EntityController<T>`, so validation,
69 * authorisation, entity construction, SQL execution, JSON marshalling and
70 * error→HTTP mapping all live in that base. The template parameter supplies the
71 * table name, SQL statements and permission queries used there. This class
72 * exists to give service entities a distinct interface (and therefore a
73 * distinct entry in the route registry) from appointment entities.
74 *
75 * Plain-language version: `T` is whichever entity class we are
76 * handling (say `Clinics`). The `Service_t` after `template` is a "concept" — a
77 * compile-time check that refuses to build this class unless `T` is really a
78 * service type. Because this class stores no data ("stateless"), its only job
79 * is to hand the arguments to `EntityController<T>` and let that base do
80 * everything.
81 *
82 * Explicit instantiations are provided for `Clinics`, `Pharmacies`,
83 * `Laboratories` and `RadiologyCenters`; the route layer stores
84 * `shared_ptr<ServiceController<T>>` values in a variant and dispatches to them
85 * through @ref ServiceControllerBase.
86 * @note Copy and move are disabled so each registered controller has a single
87 * identity.
88 * @see EntityController, ServiceControllerBase, Service_t
89 */
