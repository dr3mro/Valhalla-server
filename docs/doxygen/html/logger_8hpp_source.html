1/**
2 * @file logger.hpp
3 * @brief Drogon/Trantor logging bridged to an asynchronous spdlog logger.
4 * @details Declares the Logger class, which owns one asynchronous spdlog logger
5 * and configures it at construction time. The logger can write to a
6 * rotating file, a coloured console, or both, based on the server
7 * configuration. Constructing it initialises spdlog's worker thread
8 * pool, registers the logger by name, makes it spdlog's default and installs it
9 * as Trantor's spdlog backend. The log() method forwards a Trantor
10 * record at the matching spdlog severity. A colour enum and several size/thread
11 * constants support the setup.
12 *
13 * WHY THIS FILE MATTERS IN THE SERVER:
14 * This class is the single logging hub for the whole process. Framework
15 * messages from Drogon/Trantor, utility messages from Message and application
16 * messages all end up in the same sinks with the same format. It is meant to be
17 * created once as a process-wide singleton through Store; spdlog registration
18 * is global, so two instances would clash. Without it there would be no
19 * unified, non-blocking log output for the server.
20 *
21 * CONCEPTS TO LEARN (for beginners):
22 * - std::shared_ptr: https://en.cppreference.com/w/cpp/memory/shared_ptr
23 * - spdlog asynchronous logging:
24 * https://github.com/gabime/spdlog/wiki/5.-Asynchronous-logging
25 * - enum types: https://en.cppreference.com/w/cpp/language/enum
26 * - static constexpr members:
27 * https://en.cppreference.com/w/cpp/language/static#Static_data_members
28 *
29 * @author Amr Osman <dr3mro@gmail.com>
30 * @date 2026-11-16
31 */

54/**
55 * @class Logger
56 * @brief Routes Drogon/Trantor log records through an asynchronous spdlog
57 * logger.
58 * @details Owns one spdlog `async_logger` writing to a rotating file sink
59 * and/or a colour console sink, selected from Configurator's ServerConfig.
60 * Construction initialises spdlog's shared thread pool, registers the
61 * logger by name, and installs it as both spdlog's default logger and
62 * Trantor's spdlog backend, so framework, utility and application
63 * records all use the same sink configuration.
64 *
65 * Intended as a process-wide singleton created by Server through
66 * `Store`; spdlog registration is global, so more than one instance
67 * would try to register the same name twice. Logging itself is
68 * thread-safe via spdlog's sinks and worker pool.
69 * @note The file path is `log_dir` concatenated with `log_file` from
70 * ServerConfig; rotation occurs at MAX_LOG_SIZE bytes across
71 * MAX_LOG_FILES files.
72 * @see Message, Server, Configurator
73 */

78 * @brief Builds, configures and globally registers the asynchronous logger.

81 * the console and rotating-file sinks with a shared pattern, adds
82 * only the sinks enabled by `log_to_console` / `log_to_file`, then
