2 * @file logger.hpp
3 * @brief Drogon/Trantor logging bridged to an asynchronous spdlog logger.
4 * @details Declares the Logger class, which owns one asynchronous spdlog logger
5 * and configures it at construction time. The logger can write to a
6 * rotating file, a coloured console, or both, based on the server
7 * configuration. Constructing it initialises spdlog's worker thread pool,
8 * registers the logger by name, makes it spdlog's default and installs it
9 * as Trantor's spdlog backend. The log() method forwards a Trantor record
10 * at the matching spdlog severity. A colour enum and several size/thread
11 * constants support the setup.
12 *
13 * WHY THIS FILE MATTERS IN THE SERVER:
14 * This class is the single logging hub for the whole process. Framework messages
15 * from Drogon/Trantor, utility messages from Message and application messages all
16 * end up in the same sinks with the same format. It is meant to be created once as
17 * a process-wide singleton through Store; spdlog registration is global, so two
18 * instances would clash. Without it there would be no unified, non-blocking log
19 * output for the server.
20 *
21 * CONCEPTS TO LEARN (for beginners):
22 * - std::shared_ptr: https://en.cppreference.com/w/cpp/memory/shared_ptr
23 * - spdlog asynchronous logging: https://github.com/gabime/spdlog/wiki/5.-Asynchronous-logging
24 * - enum types: https://en.cppreference.com/w/cpp/language/enum
25 * - static constexpr members: https://en.cppreference.com/w/cpp/language/static#Static_data_members
26 *
27 * @author Amr Osman <dr3mro@gmail.com>
28 * @date 2026-11-16
29 */

42/**
43 * @class Logger
44 * @brief Routes Drogon/Trantor log records through an asynchronous spdlog logger.
45 * @details Owns one spdlog `async_logger` writing to a rotating file sink and/or
46 * a colour console sink, selected from Configurator's ServerConfig.
47 * Construction initialises spdlog's shared thread pool, registers the
48 * logger by name, and installs it as both spdlog's default logger and
49 * Trantor's spdlog backend, so framework, utility and application
50 * records all use the same sink configuration.
51 *
52 * Intended as a process-wide singleton created by Server through
53 * `Store`; spdlog registration is global, so more than one instance
54 * would try to register the same name twice. Logging itself is
55 * thread-safe via spdlog's sinks and worker pool.
56 * @note The file path is `log_dir` concatenated with `log_file` from
57 * ServerConfig; rotation occurs at MAX_LOG_SIZE bytes across MAX_LOG_FILES files.
58 * @see Message, Server, Configurator
59 */
60class Logger // Owns the process-wide spdlog logger; create only one instance.
61{
62 public:
63 /**
64 * @brief Builds, configures and globally registers the asynchronous logger.
65 * @details Reads ServerConfig from Configurator (via Store), initialises the
66 * spdlog thread pool (queue size THREADPOOL, THREADS workers), builds
67 * the console and rotating-file sinks with a shared pattern, adds
68 * only the sinks enabled by `log_to_console` / `log_to_file`, then
69 * registers the logger as "Project Valhalla" and enables Trantor's
70 * spdlog forwarding.
71 * @post spdlog has a registered default logger and Trantor routes to it.
72 * @warning On spdlog_ex (e.g. a duplicate registration) the error is printed
73 * to stdout and construction succeeds with logger_ unset; later
74 * log() calls would then dereference a null pointer. Construct once,
75 * before any component starts logging.
76 */
77 Logger(); // Constructor does all the setup and global registration.
