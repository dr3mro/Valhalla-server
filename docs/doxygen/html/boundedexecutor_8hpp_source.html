2 * @file boundedexecutor.hpp
3 * @brief A fixed-size worker pool with a bounded queue, plus the callback-adapting helper built on it.
4 * @details This file declares BoundedExecutor: a group of worker threads that run slow, blocking jobs such as database
5 * calls and password hashing away from Drogon's IO threads. Each worker has a short queue. If every queue is
6 * full, a new job is refused instead of being allowed to wait forever, so the server can quickly answer 503.
7 * The helper runOnExecutor() makes sure the HTTP reply is sent whether the job was accepted or refused.
8 *
9 * WHY THIS FILE MATTERS IN THE SERVER:
10 * Drogon's IO threads must stay free to accept new requests. Database and password work would block them, so callers
11 * use runOnExecutor() to hand that work to this pool. The pool reports false when full, which lets the caller answer
12 * HTTP 503 ("server busy") rather than piling up unlimited work. With zero workers, jobs run inline on the caller,
13 * which is how unit tests stay synchronous. Without this file, every slow call would stall the whole web server.
14 *
15 * CONCEPTS TO LEARN (for beginners):
16 * - Condition variables: a way for a thread to sleep until another thread wakes it with new work. https://en.cppreference.com/w/cpp/thread/condition_variable
17 * - Atomic memory order: rules for when one thread's writes become visible to another. https://en.cppreference.com/w/cpp/atomic/memory_order
18 * - Work stealing: an idle worker takes jobs from a busier worker's queue. https://en.wikipedia.org/wiki/Work_stealing
19 * - RAII: a local lock object that unlocks a mutex automatically when the scope ends. https://en.cppreference.com/w/cpp/language/raii
20 *
21 * @author Amr Osman <dr3mro@gmail.com>
22 * @date 2026-11-16
23 */

44/**
45 * @class BoundedExecutor
46 * @brief Fixed-size worker pool with a shared bounded queue for slow, blocking work.
47 *
48 * @details A fixed pool of threads with a bounded queue. It exists so that slow, blocking work (database calls, password hashing)
49 * never runs on a Drogon IO thread. submit() never blocks: it returns false when the queue is full, and the caller answers 503.
50 *
51 * Every worker has its own queue and its own lock, so submitters and workers do not all contend on one mutex. submit() picks
52 * an idle worker if there is one (so a task never waits behind a slow one while another worker sleeps), otherwise the worker
53 * with the shortest queue, so the queues stay the same length and waiting time stays fair (plain round-robin left some queues
54 * long and some short, and the tasks in the long ones waited 20 times longer). Only an idle worker is woken (a busy one needs no wake-up, it looks at
55 * its queue when it finishes). A worker that has run out of work takes tasks from the other workers' queues before it sleeps. The queue limit is shared: at
56 * most queue_max tasks wait across all workers.
57 *
58 * With zero workers every task runs inline, on the submitting thread. Unit tests use that so they stay synchronous.
59 *
60 * In plain words: imagine a fixed number of chefs (worker threads) each with their own order ticket rack
61 * (queue). New orders go to a free chef, or to the shortest rack if nobody is free. A chef with no tickets
62 * peek at other racks and helps out before going to sleep ("work stealing"). There is one overall limit on
63 * how many tickets may wait; past that, submit() says "no" immediately so the caller can send HTTP 503 rather
64 * than let the backlog grow without bound.
65 * @note Not copyable or movable; instances are kept alive by shared_ptr, typically through the Store.
66 * @see DbExecutor, PasswordWorker, runOnExecutor()
67 */

192 *
193 * @details Each worker has its own mutex so submitters and workers do not contend on a single lock. depth and idle
194 * are atomics so submit() can make scheduling decisions without locking every worker. ("Contend" means

271/**
272 * @brief Runs body(callback) on an executor, answering 503 immediately when the queue is full.
273 *
274 * @details Runs body(callback) on the executor. When the queue is full the callback is answered right away with 503 and
275 * body never runs. The callback is shared with the task so that it is still available for that reply.
276 *
277 * The callback is moved into a shared_ptr that both the queued task and this function hold. On acceptance the
278 * task runs on a worker thread (or inline when the executor has no workers) and body receives the callback as an
279 * rvalue. On rejection the callback is invoked here, on the submitting thread, with SERVICE_UNAVAILABLE and
280 * busy_message; body is destroyed without being called.
281 *
282 * In plain words: hand the slow job (body) and the HTTP reply function (callback) to the pool. If the pool
283 * takes the job, a worker runs body later and body sends the reply. If the pool is full, we send a 503 right
284 * now using the same callback. Either way the client always gets an answer, and the callback is never lost.
285 * @tparam Body Callable invocable with a CALLBACK_ (std::function<void(int, const std::string&)>); it is captured by the
286 * task, so it must be move-constructible.
287 * @param[in,out] executor Pool that will execute body.
288 * @param[in] callback Completion callback; ownership is moved into this helper.
289 * @param[in] busy_message Message paired with the 503 status on rejection.
290 * @param[in] body The blocking work to run on the pool.
291 * @note Because the callback is moved into the task, callers must not use it after passing it here.
292 * @see BoundedExecutor::submit(), runOnDbExecutor(), runOnPasswordWorker()
293 */
294template <typename Body>
295void runOnExecutor(BoundedExecutor& executor, CALLBACK_&& callback, const char* busy_message, Body&& body)
296{
297 auto shared_callback = std::make_shared<CALLBACK_>(std::move(callback)); // store it once so both paths can use it
298 if (!executor.submit([shared_callback, task = std::forward<Body>(body)]() mutable { task(std::move(*shared_callback)); })) // false means the pool is full
299 {
300 (*shared_callback)(api::v2::Http::Status::SERVICE_UNAVAILABLE, busy_message); // rejected: answer 503 here and never run body
301 }
302}
